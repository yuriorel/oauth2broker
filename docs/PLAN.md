# PLAN: OAuth 2 / OIDC Broker

Status: Approved. Phases 0-3 complete. Amended with OpenAPI documentation (springdoc).

## 1. Scope

A standalone OAuth 2.0 / OpenID Connect authorization server exposed as a REST API. It authenticates users itself with a minimal login form and issues its own tokens.

In scope (MVP):

- Authorization code flow with PKCE (S256, required for every client).
- Endpoints: `authorization`, `token`, `revoke`, `userinfo`.
- Supporting endpoints that clients need to verify RS256 tokens: `/.well-known/openid-configuration` and `/jwks`.
- Token endpoint grants: `authorization_code` and `refresh_token` (the refresh token is issued, so it must be redeemable).
- Client authentication at token and revoke: `client_secret_basic`, `private_key_jwt` (RFC 7523) and `none` (public clients, PKCE only).
- Storage: Redis on `localhost:6379`.
- TLS with a self-signed certificate.
- OpenAPI 3 description of the API, generated from the code (code-first) and served at `/v3/api-docs`.

Out of scope: dynamic client registration, consent screen, SSO session or cookies, implicit/hybrid/client-credentials/device flows, introspection, logout, admin UI, upstream IdP federation.

## 2. Decisions

| Topic | Decision |
|---|---|
| Language | Java 25, `--enable-preview` (needed for structured concurrency, JEP 505) |
| Build | Maven, with the Maven Wrapper (`mvnw`), single module |
| Framework | Spring Boot (latest 4.x GA, exact version checked on Maven Central at scaffold time), Spring Web MVC, `spring.threads.virtual.enabled=true` |
| OAuth implementation | Hand-written endpoints. Spring Authorization Server is **not** used, because it would hide the protocol logic and the Java features this project is meant to show. Spring Security is not used for the endpoints either; only `spring-security-crypto` for BCrypt. |
| JOSE | Nimbus JOSE + JWT |
| Redis client | Spring Data Redis (Lettuce), `StringRedisTemplate`, JSON values via Jackson |
| Access token | JWT, RS256, 15 min TTL. The `jti` is recorded in Redis, so revocation and userinfo check that it is still present. |
| Refresh token | Opaque, 256-bit random, stored in Redis under its SHA-256 hash, 30 day TTL, rotated on every use |
| ID token | JWT, RS256, includes `nonce`, `at_hash` |
| Authorization code | Opaque, 60 s TTL, single use (Redis `GETDEL`) |
| Signing key | RSA 2048 key pair in a PKCS12 keystore, alias `signing`, `kid` derived from the JWK thumbprint |
| TLS | Self-signed cert in the same PKCS12 keystore, alias `tls`, port 8443. Generated by a `keytool` script. |
| Client and user data | Seeded into Redis at startup from `seed.json` (idempotent). No registration endpoint. |
| Login page | One HTML page rendered from a text block. No template engine. |
| API docs | Code-first OpenAPI with springdoc-openapi (`springdoc-openapi-starter-webmvc-api`, latest 3.x for Boot 4). Generated from the controllers plus `@Operation`/`@Parameter`/`@ApiResponse` annotations. Served at `/v3/api-docs` (JSON) and `/v3/api-docs.yaml`. No Swagger UI (not requested). |
| Tests | JUnit 5, AssertJ, Mockito (unit, Surefire); Playwright for Java (integration, Failsafe, `*IT`); JaCoCo |
| Base package | `com.oauth2broker` |

## 3. Architecture

```
Browser / Client
     |  HTTPS :8443
     v
Spring MVC controllers (virtual threads)
  AuthorizationController  GET/POST /authorize
  TokenController          POST /token
  RevocationController     POST /revoke
  UserInfoController       GET/POST /userinfo
  DiscoveryController      GET /.well-known/openid-configuration, GET /jwks
  springdoc (generated)    GET /v3/api-docs, GET /v3/api-docs.yaml
     |
RequestContextFilter -- binds ScopedValue<RequestContext> (request id, issuer)
     |
Services
  ClientAuthenticator      (sealed ClientCredentials -> ClientRegistration)
  AuthorizationService     (validate request, login, issue code)
  TokenService             (sealed TokenRequest -> TokenResponse)
  TokenSigner / KeyStoreKeys
     |
Repositories over StringRedisTemplate
  ClientRepository, UserRepository, AuthRequestRepository,
  CodeRepository, TokenRepository, AssertionReplayRepository
     |
Redis :6379
```

Packages (one per feature): `authorize`, `token`, `revoke`, `userinfo`, `discovery`, `client`, `user`, `jose`, `store`, `web` (filter, error handling, request context), `config` (properties, `OpenApiConfig`).

### 3.1 Redis keys

| Key | Value | TTL |
|---|---|---|
| `client:{client_id}` | `ClientRegistration` JSON | none |
| `user:{username}` | `User` JSON (BCrypt hash + claims) | none |
| `authreq:{id}` | pending `AuthorizationRequest` JSON | 10 min |
| `code:{code}` | `AuthorizationCode` JSON | 60 s |
| `at:{jti}` | `AccessTokenRecord` JSON (client, user, scope) | 15 min |
| `rt:{sha256(token)}` | `RefreshTokenRecord` JSON | 30 days |
| `assertion:{client_id}:{jti}` | `1` (replay guard, `SET NX`) | until assertion `exp` |

### 3.2 Flows

**Authorize (GET /authorize).** Validate `client_id`, the exact `redirect_uri`, `response_type=code`, `scope`, `code_challenge` and `code_challenge_method=S256`. Errors in `client_id` or `redirect_uri` return a 400 page. Every other error redirects back with `error` and `state`. A valid request is stored as `authreq:{id}`, and the login page is rendered with that id in a hidden field.

**Login (POST /authorize).** Verify the username and password. Load and delete `authreq`, issue a code, then send a 302 to `redirect_uri?code=...&state=...&iss=...` (RFC 9207).

**Token (POST /token).**
1. Parse the form into a sealed `TokenRequest` (`AuthorizationCodeGrant`, `RefreshTokenGrant`) and a sealed `ClientCredentials` (`SecretBasic`, `PrivateKeyJwt`, `PublicClient`).
2. Authenticate the client. For `private_key_jwt`, check the signature against the client's registered JWKS and verify that `iss` and `sub` equal `client_id`, that `aud` contains the issuer or the token endpoint URL, `exp`, and a single-use `jti`. Only RS256 and ES256 are accepted.
3. Code grant: `GETDEL` the code, then check the client, `redirect_uri` and PKCE verifier. Issue the access token, refresh token and, if `openid` was requested, the ID token.
4. Refresh grant: check the client binding, rotate the token, and keep or narrow the scope.
5. Respond with `Cache-Control: no-store`. Errors follow RFC 6749 section 5.2 (`invalid_client` gives 401 with `WWW-Authenticate`).

**Revoke (POST /revoke, RFC 7009).** Authenticate the client. The `token_type_hint` decides which lookup runs first. Delete `at:{jti}` or `rt:{hash}` if the token belongs to this client. Always respond 200.

**UserInfo (GET/POST /userinfo).** Read the Bearer token, verify its signature, `exp`, `iss` and the presence of `at:{jti}`, and require the `openid` scope. Return `sub` plus the claims allowed by `profile` and `email`. Errors use `WWW-Authenticate: Bearer error=...` (RFC 6750).

### 3.3 OpenAPI

`OpenApiConfig` defines one `OpenAPI` bean with the title, version, the server `https://localhost:8443` and two security schemes: `clientSecretBasic` (HTTP basic, for `/token` and `/revoke`) and `bearerAuth` (HTTP bearer JWT, for `/userinfo`). `private_key_jwt` is described through the `client_assertion` and `client_assertion_type` form parameters. Each controller method has an `@Operation` summary, its form or query parameters with OAuth names and required flags, and its responses: success, the RFC 6749/6750 error body, and redirects for `/authorize`. Form endpoints declare `application/x-www-form-urlencoded`. The `/v3/api-docs` endpoints are left out of the generated document.

### 3.4 Where each Java feature is used

| # | Feature | Use |
|---|---|---|
| 1 | Virtual threads | `spring.threads.virtual.enabled=true` (Tomcat request handling, structured-concurrency subtasks) |
| 2 | Structured concurrency | `TokenService`: authenticate the client and load the code/refresh record concurrently. `UserInfoController`: check `at:{jti}` and load the user concurrently. Uses `StructuredTaskScope.open()`. |
| 3 | Records | All domain objects, requests, responses (also used as OpenAPI response schemas), Redis values, config properties (`@ConfigurationProperties` record) |
| 4 | Sealed types | `TokenRequest`, `ClientCredentials`, `OAuthError` hierarchy, `AuthorizeOutcome` (login page / error redirect / error page) |
| 5 | `var` | Local variables throughout |
| 6 | Switch expressions | Grant-type parsing, error-to-HTTP-status mapping, scope-to-claims mapping |
| 7 | Pattern matching | `switch` with record deconstruction over `TokenRequest` and `ClientCredentials`; `instanceof` patterns on JWK types (RSA/EC) |
| 8 | Text blocks | Login HTML page, test fixtures (JSON, JWT claims) |
| 9 | Unnamed `_` | Ignored record components in patterns, `catch (... _)` |
| 10 | Stream gatherers | Seed loading with `Gatherers.mapConcurrent` (parallel Redis writes on virtual threads); scope parsing with `Gatherers.fold` where it reads naturally |
| 11 | Module imports | `import module java.base;` in classes that use many JDK packages (`TokenSigner`, later `web`) |
| 12 | Scoped values | `RequestContext` (request id, issuer URL) bound per request in a filter, read by services and inherited by structured-concurrency subtasks. Replaces `ThreadLocal`. |
| 13 | Flexible constructor bodies | `SigningKey(RSAPublicKey, PrivateKey)` builds the thumbprint-keyed JWK before `this(...)`; `OAuthException` subclasses validate and normalize arguments before `super(...)` |

If a feature does not fit naturally where listed, it moves or is dropped. Forced usages will not be added.
